# 주식 자동매매 앱 요구사항 정의서

시중의 자동매매 도구(증권사 제공 시스템트레이딩, 개인 개발자 앱, 오픈소스 트레이딩 봇)가
공통적으로 갖추고 있는 기능을 정리하고, 이 프로젝트가 그중 무엇을 구현했는지 표시했습니다.

구현 상태 표기: ✅ 구현됨 / 🟡 부분 구현 / ⬜ 미구현(확장 지점)

---

## 1. 왜 이 목록인가

자동매매 앱의 기능은 성격이 다른 세 덩어리로 나뉘고, 각각 실패했을 때의 결과가 다릅니다.

| 영역 | 실패했을 때 생기는 일 |
|---|---|
| **연결(브로커 API)** | 주문이 아예 나가지 않거나, 인증이 끊겨 장중에 멈춤 |
| **판단(전략·지표)** | 기대와 다른 시점에 사고팜 — 손실은 나지만 통제 가능 |
| **통제(리스크·한도)** | **계좌가 망가짐.** 되돌릴 수 없음 |

시중 도구들이 전략 종류보다 **한도 설정 화면에 더 많은 공을 들이는 이유**가 여기 있습니다.
자동매매 사고의 대부분은 전략이 틀려서가 아니라 한도가 없어서 발생합니다.
이 프로젝트도 같은 우선순위를 따랐습니다.

## 3. 비기능 요구사항

| ID | 요구사항 | 이 프로젝트의 대응 |
|---|---|---|
| N-01 | **인증정보 보호** | Android Keystore 암호화 저장, 백업 제외, 릴리스 빌드 본문 로깅 차단 |
| N-02 | **판단 재현성** | 백테스트와 실거래가 `TradingEngine` 하나를 공유 |
| N-03 | **미래 참조 금지** | 백테스트는 종가 판단 → 다음 봉 시가 체결 |
| N-04 | **부분 실패 격리** | 한 종목의 오류가 전체 루프를 멈추지 않음 |
| N-05 | **추적 가능성** | 모든 판단·거절 사유를 매매일지에 기록 |
| N-06 | **테스트 용이성** | 매매 로직은 안드로이드 비의존 순수 Kotlin 모듈 (JVM 단위 테스트 60건) |
| N-07 | **호출 한도 준수** | 초당 호출 제한 인터셉터 |

## 4. 알려진 한계 — 반드시 읽어주세요

이 앱은 **모바일 단독** 구조입니다. 아래는 설계상 피할 수 없는 한계이며,
"기능이 부족한 것"이 아니라 "구조가 가진 성질"입니다.

1. **기기가 꺼지면 매매도 멈춥니다.**
   배터리 방전, 기내 모드, 제조사 배터리 최적화로 인한 서비스 강제 종료 시
   **손절 주문도 나가지 않습니다.** 포그라운드 서비스와 웨이크락으로 확률을 낮췄을 뿐입니다.
   → 실계좌 운용 시에는 증권사 앱에서 **별도의 스탑로스 주문을 병행**하세요.

2. **폴링 방식이라 체결 감지가 즉각적이지 않습니다.**
   실행 주기(기본 60초)만큼 지연됩니다. 급변동 구간에서는 의도한 가격에 손절되지 않을 수 있습니다.

3. **진행 중인 봉으로 판단합니다.**
   장중 신호를 얻기 위해 확정되지 않은 봉을 쓰므로, 신호가 생겼다 사라질 수 있습니다.
   재주문 쿨다운으로 억제하지만 완전히 없앨 수는 없습니다.

4. **백테스트 결과는 미래를 보장하지 않습니다.**
   수수료·세율·슬리피지 가정이 실제와 다르면 결과가 크게 달라집니다.
   전략 간 **상대 비교용**으로만 쓰세요.

무중단 운용이 목적이라면 매매 루프를 서버(상시 구동 환경)로 옮기고
모바일 앱은 조회·제어 콘솔로 두는 구조가 맞습니다. 이 프로젝트의 `core-trading` 모듈은
안드로이드에 의존하지 않으므로 서버로 그대로 옮길 수 있습니다.
